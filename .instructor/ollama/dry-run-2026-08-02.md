Record of the first end-to-end test of the Day 4 shared-Ollama setup on the Yens.
Covers `start_ollama_server.sh`, the new `ensure_ollama_server.sh`, and the CPU
contrast server. Written so the next person does not have to rediscover the four
things that broke.

**Environment.** Yens; login node `yen4`; `gpu` partition = `yen-gpu1` (A30, 4×24 GiB),
`yen-gpu2`/`yen-gpu3` (A40, 4×48 GiB), `yen-gpu4` (H200, 2×141 GiB) = 14 GPUs total.
`curl 7.81.0`, `jq 1.6`, `apptainer` via `ml apptainer`.

## Bugs found and fixed

1. **`curl --json` does not exist on the Yens.** `--json` arrived in curl 7.82.0
   (Mar 2022); the cluster runs 7.81.0 (Jan 2022) on login *and* compute nodes.
   Every student following the page would have hit
   `curl: option --json: is unknown` simultaneously. Replaced with
   `-H 'Content-Type: application/json' -d '…'` in all three places:
   `docs/day4/running-llms.md` (student-facing), and the board banners in
   `start_ollama_server.sh` and `ensure_ollama_server.sh`.

2. **A bound port is not a working server.** `start_ollama_server.sh` runs
   `ollama pull` *after* its readiness poll, so there is a window — minutes wide
   on a cold cache — where `GET /` returns `Ollama is running` while `/api/tags`
   is `{"models":[]}` and every query returns
   `model 'llama3.2:3b' not found`. `ensure_ollama_server.sh` originally probed
   the port and announced the URL during exactly that window. Its health check
   now probes `/api/tags` for the model. **This is the one to remember:** the
   window opens precisely when the class first curls the URL.

3. **An inherited `SCRATCH_BASE` silently wins.** `${SCRATCH_BASE:-…}` yields to
   whatever is already exported, and DARC's rcpedia guide still instructs
   `export SCRATCH_BASE=/scratch/shared/$USER` — the *superseded* per-user path.
   Commit `f34a9dd` changed only the default, so the fix does not hold in the
   shell you would actually be in. Both directories exist, so it fails quietly.
   `ensure_ollama_server.sh` now warns. (Per-user scratch is
   `/scratch/users/<user>/`; `/scratch/shared/<project>/` dataset paths are a
   different thing and unaffected.)

4. **`--output` cannot go to `/tmp`.** `/tmp` is node-local (`/dev/md0`), so a
   job's stdout written there is invisible from the login node. Use a path under
   shared scratch.

## Not verified — do not assume these

- **CPU inference was never exercised.** No chat request was sent to the CPU
  server; only the `/api/tags` probe. That it *serves* is untested, and per
  bug 2 above, a passing probe is not proof a server answers.
- **No GPU-vs-CPU timing.** The runtime contrast the demo rests on is unmeasured.
- **`num_ctx` on the cards you will actually teach from.** The
  `default_num_ctx=262144` observed is VRAM-derived on a 141 GiB H200; an A30
  (24 GiB) will default lower. This is what the silent-truncation trap in
  `TODO.md` turns on, and SEC filings are long.
- **Cold-cache pull timing.** The model pulled in ~15 s for 1.9 GB, implying a
  warm blob cache. A genuinely cold pull (post scratch purge) is untimed.
- **Concurrency.** Twenty simultaneous clients against one 3B model: untested.
- **Login-node → login-node.** Not run; inter-node `ssh` needs a key that was
  not available. Cross-node reach was shown from a compute node instead.
- **Jekyll rebuild** after the `running-llms.md` edit: not run.

## Operational notes

- `ensure_ollama_server.sh` defaults to `WALLTIME=4:00:00` against a ~3-hour Day 4.
  The GPU is held for the whole walltime whether queried or not.
- It avoids `yen-gpu4` by default: the H200s are the scarcest hardware on the
  cluster and a 3B model does not need one.
- Two servers require two `SCRATCH_BASE` trees — `ollama.sh` keeps
  `port.txt`/`host.txt`/`models` under a single `${SCRATCH_BASE}/ollama`, so
  sharing one would overwrite the first server's coordinates.
- `/scratch/users/$USER` is mode 700, so students cannot read the coordinate
  files. Reading the URL out to the room is the intended arrangement.
